# CI: Build & Test Spec

## Overview

The first stage of the project's CI/CD pipeline and the first piece of infrastructure outside the app itself. Every pull request into `main` (and every push to `main`) triggers a GitHub Actions workflow that builds the app and runs the full Swift Testing suite on an iOS Simulator. `main` is then protected by a ruleset: the only way in is a PR whose CI check is green.

This is feature 1 of a staged CI/CD roadmap. It stays deliberately minimal: one workflow, one job, raw `xcodebuild`. Later stages add linting, coverage, caching, fastlane, and a release pipeline. No paid Apple Developer account exists, so nothing here signs code: simulator builds don't need signing.

## Constraints & Decisions

- **The repository becomes public.** On GitHub Free, a private repo gets 2,000 Actions minutes/month and macOS jobs burn them at 10x (≈200 macOS minutes). Rulesets and branch protection are also unavailable for private repos on Free. A public repo gets unlimited standard-runner minutes and rulesets. The history was scanned for secrets before publishing and none were found.
- **Runner: `macos-26` (ARM64), Xcode pinned to 26.3.** This matches the local toolchain (Xcode 26.3, build 17C529), so CI and local builds use the same compiler. The runner's default Xcode (26.6 at time of writing) drifts as GitHub updates images. Pinning prevents "the CI broke by itself" surprises. Select it with `DEVELOPER_DIR=/Applications/Xcode_26.3.app/Contents/Developer`.
- **Destination: `iPhone 17 Pro Max`, iOS 26.2.** It is present both locally and on the runner image with Xcode 26.3.
- **`CODE_SIGNING_ALLOWED=NO`.** Simulator builds don't need a signing identity, and the runner has none.
- **Pin third-party actions to a full commit SHA** (with the version in a trailing comment), not a movable tag like `@v5`. This is the production-grade supply-chain practice: a tag can be re-pointed, a SHA cannot. Dependabot (roadmap stage 5) keeps the SHAs fresh.
- **Least-privilege token:** `permissions: contents: read` at the workflow level.

## Requirements

### 1. Repository hygiene (prerequisites for a clean CI checkout)

- **Share the `rick-verse` scheme.** Today it exists only implicitly (autogenerated by Xcode, no `.xcscheme` on disk). Mark it Shared (Xcode → Product → Scheme → Manage Schemes… → Shared). This produces `rick-verse.xcodeproj/xcshareddata/xcschemes/rick-verse.xcscheme`, which gets committed. Confirm the `Tests` target is in the scheme's Test action.
- **Commit `Package.resolved`.** `.gitignore:43` (`*.xcworkspace`) currently hides `rick-verse.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`, so CI would resolve Kingfisher fresh on each run and could pick a different version than local. Re-include the project workspace in `.gitignore` (`xcuserdata/` still keeps per-user state out) and commit the lock file.

### 2. Workflow: `.github/workflows/ci.yml`

- **Name:** `CI`. **Job id:** `build-and-test`. This becomes the status-check name the ruleset requires, so it must stay stable.
- **Triggers:**
  - `pull_request` targeting `main`
  - `push` to `main`, so `main` has its own green/red history after each merge
  - `workflow_dispatch`, for manual re-runs from the Actions tab
- **Concurrency:** group by workflow + ref with `cancel-in-progress: true`. A new push to a PR cancels the now-stale run.
- **No `paths-ignore`.** A required check that is skipped by a path filter never reports, which blocks docs-only PRs forever. Minutes aren't scarce on a public repo, so every PR runs CI.
- **Job:** `runs-on: macos-26`, `timeout-minutes: 30`, Xcode pinned via `DEVELOPER_DIR`.
- **Steps:**
  1. Checkout (`actions/checkout`, SHA-pinned)
  2. Print toolchain info (`xcodebuild -version`, `xcrun simctl list runtimes`), so a failure's log starts with what ran
  3. `xcodebuild test` against the shared scheme and pinned destination, with `-resultBundlePath`, `CODE_SIGNING_ALLOWED=NO`, and per-test timeouts (`-test-timeouts-enabled YES -maximum-test-execution-time-allowance 60`). A hung async test fails the test instead of burning 30 runner minutes.
  4. Upload the `.xcresult` bundle as an artifact on failure (`actions/upload-artifact`, SHA-pinned, short retention). Open it locally in Xcode to see exactly which test failed and why. The bundle is written to `build/` and that folder is uploaded: `upload-artifact` strips the common root, so uploading the `.xcresult` itself would ship only its contents and the download wouldn't open as a bundle. This was found on the deliberate red run.

### 3. Protect `main` (GitHub UI, done by the user)

A repository ruleset targeting the default branch:
- Require a pull request before merging (0 required approvals; this is a solo project)
- Require status checks to pass: `build-and-test`; require branches to be up to date
- Block force pushes; restrict deletions
- No bypass list. The rules apply to the admin too. That's the point.

### 4. Process change

Merging moves from local `git merge` to **merging the PR on GitHub**. Direct commits to `main` (e.g. the `chore: reset current-feature.md` commits) are no longer possible; they go on the feature branch before the PR is merged. Update `context/ai-interaction.md` (Workflow steps 6–8) to describe: push branch → open PR → CI green → merge PR on GitHub → pull `main` locally → delete branch. Recommended: install the GitHub CLI (`brew install gh`, then `gh auth login`) to open and merge PRs from the terminal.

## Verification

1. Workflow runs on the PR for this feature and goes green.
2. **Deliberate red:** push a temporary commit that breaks one test. The check goes red, the merge button is blocked, and the `.xcresult` artifact is attached. Revert the commit, the check goes green, and merge becomes possible.
3. After merge, the `push` run on `main` is green.
4. A direct `git push origin main` is rejected by the ruleset.

## Out of Scope (later roadmap stages)

- SwiftLint, code coverage reports/thresholds, SPM/DerivedData caching, log formatting (`xcbeautify`)
- fastlane
- Versioning, tags, GitHub Releases, archives
- Dependabot
- Anything requiring signing (TestFlight, App Store). That is covered by a later learning guide.

## Observations (not fixed here)

- Tests emit Swift 6 warnings in `CharacterMappingTests`: "main actor-isolated conformance of 'RMCharacter.Status' to 'Equatable' cannot be used in nonisolated context".
- The project's build settings drift from the spec: `SWIFT_VERSION = 5.0` (spec: Swift 6), deployment targets 18.0 / 26.2 (spec: iOS 17+).
- `rick-verse.xcodeproj/xcuserdata/…/xcschememanagement.plist` is tracked despite `xcuserdata/` in `.gitignore` (added before the rule).

## Learning Notes

- **Runner:** a fresh, disposable VM per job. Nothing from your Mac exists there. That is why the scheme and `Package.resolved` must be in git.
- **Job vs step:** a job is one VM; steps run sequentially inside it and share its filesystem. A failed step fails the job, and later steps are skipped unless they declare `if: failure()` / `if: always()`.
- **Status check:** each job reports a check on the commit. Rulesets refer to checks by job name, which is why the job id is part of this contract.
- **Why pin Xcode and SHAs:** reproducibility and supply-chain safety. A pipeline should change only when you change it.
